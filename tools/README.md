# Tools

Small scripts for the few things that must be done exactly: compiling against the shared build, changing the shared library safely, building it, and checking the targets. How to do the mathematics is up to the agents; nothing here decides it.

What must hold, and why, is written in `AGENTS.md` §3 and in the role documents. The scripts are one way to carry it out. The usage of each script is in the comment at its top.

## Changing the tools

The scripts were written for one machine and one project, and may be changed to fit the project at hand: another DAG layout, another layout of the Lean project, a limit that is too tight, a check that refuses correct work or misses wrong work.

The maintainer decides on a change and makes it, since every agent runs the same scripts and a change reaches all of them at once. Leads report what does not fit to the maintainer, workers to their lead. The maintainer:

- keeps what the contract asks for: a changed script still does what the role documents say the step does;
- tries the change on a copy, then replaces the script in one step, never editing it in place while others may be running it;
- updates this file in the same change, and writes one line in `coord/ledger.md`: what changed and why.

## Configuration

Two files, both committed with the project, so every machine sees the settings of the others. The launcher writes them.

`coord/sheaf.env`, for the project:

```bash
SHEAF_LIB=MyLib               # the library's top-level source directories under lean/, space separated
SHEAF_EARLY_REVIEW=0          # 1 when SETUP.md asks for an early review of the target statements: stage 2 then states the targets first
```

`coord/machines/<host name>.env`, for one machine; optional, and its values override the project's:

```bash
SHEAF_FILE_TIMEOUT=60         # seconds a single-file compile may take
SHEAF_BUILD_THREADS=3         # threads of the global build
SHEAF_BUILD_WAIT=600          # seconds the global build waits for a landing when none has arrived
SHEAF_CLAIMS_PER_GROUP=10     # claims one group may hold at once
SHEAF_CLAIM_TTL=6             # hours after which an unrenewed claim may be taken over
```

The scripts that compile and land take the name of the group from `SHEAF_GROUP`: call them as `SHEAF_GROUP=<group> tools/…`. The sandbox of a group is `lean/.sandbox/<group>/`.

## Compiling and landing

| Tool | What it is for |
|---|---|
| `blueprint_pr.py diff / cut / check` | Compare DAG text with the upstream blueprint, cut one chapter or sketch, and validate text-only structural changes. |
| `lean_file.sh <file>` | Compile one file, with 2 threads and a limit of 60 s. A library file compiled here is visible to the group's later compiles before the next global build, so a group can land a new lemma module and then the module that imports it. The group's mirror `local/build/<G>/` links the shared build's files and refreshes when `lean/.lake/build/lib/lean` is newer than its `.stamp` (`build.py` touches it on publish); a link to a module whose source still exists is kept while its file is absent, so a rebuild of the shared build in place (a base move, `lake build` outside `build.py`) no longer leaves modules missing from the mirrors (object file ... does not exist; X-mir, 2026-10-11). After such a rebuild, `touch lean/.lake/build/lib/lean` so the mirrors take its new files at once. |
| `land.sh <sandbox file> <library file>` | Put a finished file into the library. Compiles it in the sandbox and again in place, and refuses it (putting the old version back) if it removes an import or a declaration some other module still needs, adds a name another module already declares, adds a theorem whose statement the library already states word for word, or closes an import cycle. |
| `land_set.sh <set directory>` | Put a set of files into the library at once: a changed statement or definition together with the modules adapted to it. Compiles the files of the set and runs the same checks on each; the modules downstream of the set are compiled by the global build, which starts over as soon as the set has landed. |
| `landing.py status / mine <group> / revert <id> <reason>` | The landings that are being checked or wait for the global build, and the last build's result; a group's open and reverted landings; `revert` is the maintainer's. |
| `build.py [--retry]` | The global build, for the maintainer (§ The global build). When nothing has landed it waits for the next landing, and builds as soon as it arrives. After a red build, `--retry` builds the same snapshot again with the maintainer's own landings and without the landings it reverted, and nothing else. |

A single-file compile of a module cannot show its effect on other modules, because they still load its old `.olean`. That is why landing runs `import_prune_check.py`, and why every landing is verified afterwards by the global build. The check reads source text: it does not see a removed import that only provided an instance, which the build shows.

## The global build

The global build never compiles the tree the groups work in. `build.py` builds a copy, `local/buildtree/`, and brings the compiled files back, so nothing is frozen while it runs, a failed build leaves the groups' compiled files untouched, and a build can be stopped at any moment without harm. The copy shares `lean/.lake/packages` through a link and holds its own build output.

The groups and the build talk through records in `local/builds/`, the way claims are files in `coord/claims/`:

| Record | Written by | Meaning |
|---|---|---|
| `inflight/<id>.json` | `land.sh`, `land_set.sh`, when they write the files | The group is still checking the landing. A build started now takes the previous version of its files, from `backup/<id>/`. |
| `requests/<id>.json` | the same scripts, when the checks have passed | The landing waits for a build. Its kind is `interface` when it changes what other modules see (a statement, a definition, an instance or attribute, a removed import, a deleted module, any set), otherwise `proof`. |
| `done/<id>.json` | `build.py` after a green build, or `landing.py revert` | Verified, with the commit; or reverted, with the reason. Kept for a week. |
| `last.json` | `build.py` | The last build: result, commit, failing modules, and the landings that may have caused them. |

One build:

1. **Snapshot**, holding `local/tree.lock` for a few seconds: commit the tree, copy the sources into the copy, replace the files of in-flight landings by their previous version, and note which requests the snapshot contains.
2. **Build** the copy with `lake build`.
3. **Start over** when an `interface` request arrives while the running build contains none: that landing is the one most likely to break other modules, and the groups should learn it soon. A build that contains an interface landing is never stopped; what arrives during it waits for the next build. So a build is stopped at most once.
4. **Green**: publish. The changed compiled files are copied into `lean/.lake/build`, each written completely before it replaces the old one; `local/PUBLISHING` exists meanwhile, and single-file compiles wait for it. The requests of the snapshot move to `done/`.
   **Red**: nothing is published. `build.py` prints the failing modules and, for each, the landings of the snapshot it depends on, interface landings first. The maintainer makes the build green and runs `build.py --retry`. `landing.py revert` puts a landing's files back, unless one of them was changed again since.

The first build in a new copy may compile the whole library once.

## Fields of a node: who sets them

Decision of the human (2026-10-10, evening): a delivery takes each existing node file as it is on `origin/sheaf-dag` and sets only the fields a split owns; every other field of an existing node is the maintainer's and comes through unchanged. This list is the authoritative one (`tools/node_fields.py` holds it as code; `preflight_delivery.py` check 9 and `merge_delivery.py` enforce it).

| Who | Fields |
|---|---|
| **A split sets** (on its item; a new node it writes whole) | `status` (unsplit → split, or mathlib for a leaf); `statement` (only a correction named in the report, `coord/delivery-errors.md` E7); `stmt_deps`; `proof` (steps `{text, uses, elementary}`); `proof_deps` (the union of the uses); `proof_origin`; `split_report` (with its `blueprint` entry and, for a step that uses another unit's statement as a generic tool, `tool_uses` = [{node, why}], which the merge copies into the node's `tool_uses` after the reviewer's judgement); `mathlib_searches`; `mathlib_match` (declaration, file, verified line) for a leaf; `mathlib_candidate` (close but not the node); `lean_candidates` (a slopmaster2 declaration reported as an attachment, for the maintainer to verify); inside `blueprint`: `from.place` when it was "unspecified", and `same_as`. On a key node also the `realized`/`realized_by` fields of the unit record. |
| **The maintainer's** (never changed by a delivery) | `id`, `kind`, `title`, `chapter`, `unit`, `source`, `merged_into`; `created` (set when a new node is merged; a delivered new node carries `created.item` = the item and nothing else of this column); `reviewed`; `lead_note`; `tool_uses`; `import_flags`; `lean`, `lean_audit`, `lean_notes`, `lean_names_rejected`; `blueprint.is` (null on every new node); `blueprint_lean`, `blueprint_lean_not_found`, `blueprint_kind`, `blueprint_order`, `blueprint_uses`, `blueprint_tags`, `blueprint_notes`, `blueprint_sketch`, `blueprint_proof_text`, `blueprint_proof_steps`; `proof_split_by`, `uses_not_cited`, `pointers`, `note`, `target`, `target_former`, `mathlib_match_withdrawn`. A key not in the first row is the maintainer's whether or not it is listed here. |

An attachment (a sorry-free declaration that states the node) is reported in `lean_candidates` and in the report; the maintainer verifies it against the sorry map and writes `lean` and `lean_audit`. A worker on the server who creates a node with an attachment seeds `lean_audit.slopmaster2.decls` with the name only (`lean_status.py` fills the rest); a remote group does not touch `lean_audit`.

## Searching Mathlib (stage 1)

The search rule (`stages/1-dag.md` §2, `coord/brief-stage1.md` §5) needs three kinds of search per node: LeanSearch, Loogle or Lean Finder, and a grep of the Mathlib source. On this machine they are the tools of the MCP server `lean-lsp` (lean-lsp-mcp, run with `uvx lean-lsp-mcp`, project path `~/weil-conjectures-slopmaster2`, with `lean_build` disabled: nothing is built here): `lean_leansearch`, `lean_loogle`, `lean_leanfinder`, `lean_local_search`, and `lean_declaration_file` / `lean_hover_info` for reading. An agent system without MCP uses the HTTP services directly: LeanSearch `https://leansearch.net` (its JSON API, see the lean-lsp-mcp source), Loogle `https://loogle.lean-lang.org/json?q=<query>`, Lean Finder `https://leanfinder.github.io`; and `rg` over `~/weil-conjectures-slopmaster2/.lake/packages/mathlib/Mathlib/`. Each query and its results are recorded in the node's `mathlib_searches` with its tool name (`leansearch`, `loogle`, `leanfinder`, `local_search`, `grep`).

## Importing the blueprint

This project's DAG was not split from the target by hand: `import_blueprint.py` wrote it from the blueprint in `literature/blueprint/master/blueprint/`. It can be run again; it replaces `dag/nodes/` and `dag/notes/` entirely, so it is for the state before stage 1 has changed any node.

| Tool | What it is for |
|---|---|
| `import_blueprint.py [--dry] [--lean-master DIR] [--lean-slopmaster2 DIR] [--mathlib DIR]` | One node per definition, theorem and lemma of the blueprint, in `dag/nodes/<chapter>/<id>.json`; remarks and section files in `dag/notes/`; the dropped edges in `dag/notes/dropped_edges.tsv`; the counts in `dag/import_report.json`. The rules are in the comment at its top and in `coord/ledger.md`. ## Stage 2

A stage-2 delivery (format decided by the lead, 2026-10-11; extended by STAGE 2 EXTRA NODES, decision of the human, 2026-10-11 05:55 UTC, `coord/STATE.md`) is a branch `deliver/<G>/<item>` with **one commit** on top of `sheaf-dag` containing only:

1. the item's module `lean/Sheaf/<Topic>/<Name>.lean`, module name `Sheaf.<Topic>.<Name>` (the declarations inside carry **no** `Sheaf.` prefix, e.g. `CategoryTheory.IsCompactObject` under `namespace CategoryTheory`), or no Lean file when the node is already a declaration of Mathlib or of the source repository;
2. the item's node file `dag/nodes/<chapter>/<item>.json`, as on the base and changed **only** in `lean` (`node_fields.py` `STAGE2_OWNS`), and in `stmt_deps` only by adding new definition nodes of the delivery (`STAGE2_ITEM_ALSO`): `{"module", "declaration", "declarations"` (optional, when several names realize the node)`, "file"` (absent for an existing declaration)`, "statement"` (the signature verbatim from the keyword up to `:=`/`where`, whitespace-normalized)`, "branch": "sheaf-dag"|"mathlib"|"slopmaster2", "by": "<G>", "date": "YYYY-MM-DD", "existing": true|false, "note"` (optional, free text)`}`;
3. (A) NEW DEFINITION NODES `dag/nodes/<chapter of the item>/<id>.json`, absent on the base, written whole by the field rule (`stage2_delivery.check_new_node`; `coord/brief-stage2.md` §5): kind definition, status split, `created` {by worker, item, date, group}, self-contained TeX statement citing its `stmt_deps`, source {document, place}, three kinds of search, `mathlib_match` null, empty proof, `blueprint.from` = the item's ancestor with via = the item's via with the item in front, `lean_audit` none, the item's chapter and unit, a `lean` record; each with its module (or `existing: true` and no module), cited by the item;
4. (B) DEPENDENCY MODULES: for a node in the item's `stmt_deps` on the base, its node file changed only in `lean` (the module's record, `existing: false`, with `note`) and its module;
5. the report `coord/reports/<G>/<item>.md` with `## Worker report`, `## Second reading by <G>`, and `## New nodes` / `## Dependency modules` naming each new node / dependency node when there are any.

**Statement corrections** (STAGE 2 STATEMENT CORRECTION, decision of the human, 2026-10-11, `coord/STATE.md`): the item is *corrected* when its `statement`, `proof`, `proof_deps` or `statement_change` differ from the base (`node_fields.correction_fields`); it may then change in `STAGE2_ITEM_CORRECTION` = statement, stmt_deps, proof, proof_deps, statement_change (stmt_deps may lose ids and gain ids of the base or new nodes; the corrected statement cites its `[id]`s in stmt_deps), and `node_fields.check_statement_change(base, head, citers)` validates the record: keys exactly date (YYYY-MM-DD), by (`<G> stage 2`), old_statement (the base statement verbatim), what, source {document, place}, citers [{id, holds: bool, note}] (exactly the base nodes whose stmt_deps or proof_deps contain the item), and old_stmt_deps / old_proof / old_proof_deps present iff that field changed (verbatim from the base), `previous` (the base's statement_change, whole) iff the base had one; proof or proof_deps changed without a statement change, or a new statement_change on an unchanged statement, is an error; an older stage-1 statement_change left as it is is not checked. The report needs `## Statement corrected` naming every citer. The preflight prints `item corrected: <n> citers, <k> marked holds:false`; the packet adds a section `## Statement corrected` before the Lean (old and new statement, what, source, the stmt_deps/proof/proof_deps diff, the citers table, the statements of two citers, holds:false first); the merge copies the five fields from the branch (refused if they moved on sheaf-dag since the base), sets `reviewed_lean.statement_corrected: true`, and `--apply-fixes DIR/<item>.statement-change.json` replaces the record (checked again).

Every module is the `lean.file` of exactly one node of the delivery; a module may import a sibling module of the delivery: the preflight and the packet compile each module on its own and print `compile: deferred: imports sibling <module>` for one whose sibling is not yet in the library; the merge lands the modules in dependency order.

## Stage 3

Since the switch to stage 3 (`~/cc1/switch-stage3.sh`) `lean/` is ONE Lake package: the source library adopted as it is on `slopmaster2` (root `WeilConjectures`, with its `Comparator/` tree) and the project's modules as a second root `Sheaf` (`SHEAF_LIB="WeilConjectures Sheaf"`). Every module of both roots is a file of Lean's module system (`module`, `public import`, `@[expose] public section`), so a module of either root may import one of the other. `lean/TargetsCheck.lean` imports the modules of the targets; `lean/Challenge.lean` holds the target statements.

A stage-3 item is a module name (`Sheaf.Paper.Foo`, `WeilConjectures.X.Y`); its delivery is the branch `deliver/<G>/<module>` with one commit (format in `tools/stage3_delivery.py`, report sections in `coord/brief-stage3.md` §6). ## Red batch recovery (2026-10-12)

`batch_land.py take-out <G> <module> <reason>` reverses delivery-owned source and records together. Added proof-import lines are preserved when their modules survive; substantive overlapping later edits trigger batch withdrawal. `batch_recovery.py` documents the exact record inventory. Withdrawal inverses only the batch commits, preserving independent maintainer changes, restores the original delivery cohort, and uses bounded halves. New arrivals are excluded from those halves. General interacting faults cannot be isolated in log₂(n)+2 tests; unresolved halves remain waiting, with a five-minute delay, while new batches proceed. ALERT/ALERT.log are local watcher files in ~/cc1, with one retained line per unresolved state.

`build.py` caches red source fingerprints (ledger-only commits do not change them), reuses compiler failures without running Lake again, and retries probe-only record repairs against the existing compiled snapshot. The last green publication is also recorded in `local/builds/published.json`. Proof-import writes refuse an open/partially landed batch and affected unverified landing requests. Existing-module instances, elaboration attributes, public-import removals/privatization and file-level options require a reader; the packet lists direct importers for individual lcompile.py checks. Tests: `SHEAF_LEAD=L-only python3 -m unittest discover -s tools -p test_red_recovery.py` (temporary git trees and fake build tables; no Lean).

Upstream dispatcher cuts may use `cut UNIT --also UNIT` to group same-chapter sections, and `--modules-file FILE` to select an exact planned layer. Inventory gives each multiply attached module one owner: the earliest section in dependency order, or its persisted map assignment. The dispatcher and publisher communicate via server `upstream-pr/ready`, `pushed`, and `feedback`; ready alone does not make dependencies available. Never use GitHub from the dispatcher host.

Upstream census warnings are reported per module without aborting unrelated sections; cut/check retain strict validation. Upstream-file candidates are omitted from inventory when declaration merging preserves the current upstream file unchanged; newly added imports accompany accepted proof changes only, not untouched upstream declarations. This prevents unchanged upstream files from inflating the proposed PR size.

Blueprint refinements: `blueprint_pr.py cut --ids <JSON list>` selects a dependency-ordered part of a large sketch. `check` rejects new folders without a statement-bearing `_section.md`, all chapter/sketch edits (including their proof objects), missing dependencies and malformed text. Mathlib leaves remain individual source citations. Run the text-only regression suite with `python3 -m unittest discover -s tools -p test_blueprint_pr.py`.
