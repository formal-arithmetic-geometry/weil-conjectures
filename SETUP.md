## Facts of this project

- The DAG in `dag/nodes/` was not written by splitting from the target: it was imported from the blueprint on 2026-10-08 by `tools/import_blueprint.py`. The blueprint's proofs were written by agents, and every imported node records that.
- A Lean declaration recorded in a node is one of the source repository (the node says which branch), found by reading the source text; nothing was compiled, and this project has no `lean/` directory.

## The machine (as of 2026-10-09)

- The project directory is this repository, branch `sheaf-dag` of `github.com/formal-arithmetic-geometry/weil-conjectures`; the launcher pushes it from another machine after every few commits. A new session clones it and reads `AGENTS.md`.
- Nothing is built here: there is no `lean/` and no Lake build. The Lean of the source repository is only read, from two compiled checkouts on the machine: branch `master` at `~/weil-conjectures` and branch `slopmaster2` at `~/weil-conjectures-slopmaster2`, at commit `71d63dcf6` since 2026-10-10 (before: `1ad77be9`; same Mathlib, `lake-manifest.json` unchanged); Mathlib for searching is `~/weil-conjectures-slopmaster2/.lake/packages/mathlib/Mathlib/` (the version the source repository pins, `leanprover/lean4:v4.33.1`). Workers read these paths read-only; on another machine, put the checkouts where you like and give the paths in the brief.
- The sorry maps (which declarations contain `sorry`, and what they use) are in git, compressed, in `local/`; how to regenerate them from a compiled checkout is in `tools/README.md`.
- `literature/` is rebuilt by `tools/fetch_literature.sh` (see `literature/LIST.md`). `pdftotext` (poppler-utils) is installed for the PDFs.
- Lean search tooling (installed 2026-10-09, after the first evening batches): the MCP server `lean-lsp` (lean-lsp-mcp; project path `~/weil-conjectures-slopmaster2`, `lean_build` disabled) gives the tools `lean_leansearch`, `lean_loogle`, `lean_leanfinder` and `lean_local_search` (plus reading tools such as `lean_declaration_file` and `lean_hover_info`); `uv` and `ripgrep` are installed; the plugin `lean4@lean4-skills` (skills and agents for writing Lean) is installed for stages 2 and 3 and is not used in stage 1. Rule of the human: the server is used for searching and reading goals only; it must not open or change files of the two source checkouts in a way that builds anything; nothing is built here. Without the MCP server (a Codex session, another agent system), the same services have HTTP endpoints: LeanSearch at `https://leansearch.net` (JSON API used by lean-lsp-mcp), Loogle at `https://loogle.lean-lang.org` (`/json?q=<query>`), Lean Finder at `https://leanfinder.github.io`; install lean-lsp-mcp (`uvx lean-lsp-mcp`) or call these directly, and grep Mathlib with `rg`.
- Agents: this run used Claude Code, with workers as sub-agents (the `Agent` tool, model `opus`, effort `medium`, started with the brief `coord/brief-stage1.md` as their prompt). In another agent system a worker is any separately started agent given that brief and its item as its prompt, with the same read and write permissions; "model" and "effort" are whatever that system calls the choice of model and reasoning budget. Nothing else here depends on the agent system.

## Requirements of the human (2026-10-09)

- **Sessions.** One session runs the project: it is the maintainer and the only lead, and gives items to at most 10 workers at a time, started as sub-agents with model `fable`.
- **The main session only dispatches (decision of the human, launcher 2026-10-11 16:40 +08).** The main session does no long task: it only receives (launcher messages, deliveries, sub-agents' results) and dispatches sub-agents. A main turn is a few tool calls (look at what arrived, launch or relaunch sub-agents, stop); no reading of node files or Lean, no JSON repair, no writing of statements, no tool development, no long shell command. Every piece of work is a sub-agent's (reviews that merge or return themselves, tool fixes one background sub-agent at a time, sorting of parked items, bookkeeping). When a sub-agent finishes, the main session starts the next one on the oldest waiting thing. A main turn longer than five minutes is a fault the launcher interrupts (`roles/maintainer.md`, "The main session only dispatches").
- **Stages 1 and 2 are open (decision of the human, 2026-10-11 ~04:45 UTC; replaces "Only stage 1 is open").** The stage-1 queue of the target emptied at 04:2x UTC; stage 2 (`stages/2-statements.md`) opened for the lead and for the remote groups: Lean statements from Mathlib upward, every proof `sorry`, real definitions. The Lean of the source repository is still read, never changed: branch `master` in `~/weil-conjectures`, branch `slopmaster2` in `~/weil-conjectures-slopmaster2` (at `71d63dcf6`, compiled). Mathlib for searching is in `~/weil-conjectures-slopmaster2/.lake/packages/mathlib`.
  - **The Lean project** is `lean/` in this repository: the Lake package `sheaf-weil` (toolchain `leanprover/lean4:v4.33.1`, the source's), library root `Sheaf` (`globs = ["Sheaf.+"]`: every module under `lean/Sheaf/` is built), a path dependency on `/home/ubuntu/weil-conjectures-slopmaster2` with `packagesDir` pointing at that checkout's `.lake/packages`, so that `lake build` reuses every compiled module of Mathlib and of the source library and rebuilds nothing of them (2805 cached jobs at creation). `SHEAF_LIB=Sheaf` in `coord/sheaf.env`; `lean/.lake/` and `lean/.sandbox/` are not in git; the sources under `lean/` are. The root `Sheaf` mirrors the source root `WeilConjectures` directory by directory (`Sheaf/AlgebraicGeometry/…`, `Sheaf/CategoryTheory/…`, …; what is specific to the paper under `Sheaf/Paper/`, the targets under `Sheaf/Targets/`), with the source's conventions (docstring with the source and the tag `(blueprint: <node id>)`, lines of at most 100 characters, its naming), so that a module goes upstream as a pull request with the rename `Sheaf.X -> WeilConjectures.X`.
  - **One definition per notion.** A node whose notion or statement has a declaration in the source repository (any `lean_audit.slopmaster2` state other than `none`: `closed`, `sorry_here`, `rests_on_sorry`, `closed_part`) is not stated again: its declaration is recorded as the node's `lean` (done for 603 nodes on 2026-10-11) and the node is not a stage-2 item. A notion that Mathlib defines is not stated again either: the worker records Mathlib's declaration as the node's `lean`. Only nodes with no declaration are items: 794 at the opening (`tools/dag_queue.py summary`, nearest to Mathlib first, no early review of the targets).
  - **How a stage-2 item is delivered and reviewed** is in `coord/brief-stage2.md` (the worker's page), `coord/STATE.md` (the line `STAGE 2 READY` with the exact commands for the remote groups: claim, compile on this server, deliver, preflight) and `coord/delivery-errors.md` (its stage-2 section). The remote groups have no compiled Lean: they compile single files on this server with `tools/compile_remote.sh` over ssh. The reviewer's question above all others: does the Lean statement say exactly what the node says, hypothesis by hypothesis and clause by clause, with the same objects; then it lands the file with `tools/land.sh`. The lead writes no statements while deliveries wait.
- **What is finished.** Each node has `lean_audit`, read from the compiled source repository (`tools/sorry_map.lean`, `tools/lean_status.py`, `dag/lean_audit.json`). A node whose state on `slopmaster2` is `closed` is finished for stage 1: its Lean exists and no `sorry` is reachable from it. It is not split further.
- **What is an item.** Every other node a target reaches (`sorry_here`, `rests_on_sorry`, `none`) is an item until every branch below it ends in a Mathlib leaf, with the search recorded, or in a `closed` node.
  - `rests_on_sorry`: each declaration in its `open` list is a statement the Lean has split off. One with no node gets a node, stated from its Lean statement and docstring, and is then an item itself.
  - `dag/lean_audit.json` lists every declaration with `sorry` on each branch; 575 of the 608 on `slopmaster2` are named by no node. Each belongs to an existing node or becomes one.
- **Do not trust how finely the blueprint is split.** An imported proof is material, not a finished split. A node counts as split only after a worker has checked it against `stages/1-dag.md`: every step names the nodes it uses or is judged elementary (`elementary` is `null` on 767 steps: nobody has judged them), and an argument a step hides becomes nodes of its own. The `import_flags` of a node say what the import already found doubtful.
- **Proofs follow the literature.** The documents are in `literature/` (`LIST.md`, `CITATIONS.tsv`, `stacks-tags-cited.tsv`, the Stacks project source in `stacks-project/`). A proof is written from the document, with the place. When a document is not there: put it in the Wanted table of `literature/LIST.md` and ask for it in `coord/HUMAN.md` first; only then write the proof yourself, marked as written by an agent.
- **The graph has 21 cycles** (`tools/check_dag.py --cycles`), from text citations that are pointers and not dependencies. They are removed first.
- **Effort of the workers (decision of the human, 2026-10-09, after two accounts hit their session limits).** Workers are launched at effort `medium` (the Agent tool's `effort` parameter), not `xhigh`, as a test of cost against quality; still 10 `fable` workers at a time. The maintainer commits after every reviewed item, so that a limit loses nothing reviewed, and keeps the numbers of both settings side by side in `coord/STATE.md`.
- **Model of the workers (decision of the human, 2026-10-09, after the third account's limit).** Workers are launched with model `opus` (the Agent tool's `model` parameter) at effort `medium`, still 10 at a time, as a test of whether `fable` is what uses the session limit so fast. The lead reviews the opus deliveries with particular care and records in `coord/STATE.md`, next to the fable numbers, what was rejected or corrected and whether the proofs are as complete and as faithful to the sources.

- **The proof route above the node level is the humans' and is not the agents' to change (decision of the human, 2026-10-09).** The blueprint folder (`literature/blueprint/master/blueprint/`) has three levels, and what an agent may change differs by level:
  1. **The 16 chapter files `sec-*/_section.md`: fixed.** Each names the chapter's key theorem, the reference whose route it follows, and the chapters it uses. No agent changes any of this: not the key theorem, not the route, not which chapters a chapter rests on. A doubt about this level goes to `coord/HUMAN.md` and work continues on the route as written.
  2. **The 389 unit files `sec-*/sk-*/_section.md`: followed unless mathematically wrong.** Each states one unit and proves it in steps that cite other units. Humans wrote most of it, and it may contain errors. The nodes of a unit realize its statement and its steps: every step of the unit's proof is carried by nodes of the DAG, and the units it cites are the ones the DAG passes through. An agent leaves a unit's route only when a mathematical error in it is established: the step, what is wrong with it, and the counterexample or the inference that fails, written in the node that meets it, confirmed by the lead on review, and reported in `coord/HUMAN.md` with the replacement route. A step that is hard, long, or absent from Mathlib is not an error. The replacement stays inside the unit: its statement and the chapter level above it do not move.
  3. **The node files inside a unit (`sec-*/sk-*/<node>.md`): free.** Below the unit's own proof, an agent may take another route, merge, bypass, and leave nodes unreached, as the stage documents allow, as long as the unit's statement and steps are still realized.
  
  Every node records its unit, and a split or a pruning that departs from level 1 or, without an established error, from level 2 is rejected on review.

- **Tiered review (stage 2, from 2026-10-11 23:05 +08; decision of the human).** `tools/review_class.py <G> <item>` prints `AUTO` or `FULL: <reason>`; `tools/review_class.py list` classifies every waiting delivery branch.
  FULL, read by a reviewer before landing exactly as before: the item is a definition, or the delivery has a new definition node, a dependency module, several modules, a corrected statement (or changed `stmt_deps`/`proof`), an `existing: true` record, a STATEMENT-DISPUTED, is the repair of a return, its automatic landing failed, or it falls in the sample (one statement in four, by a hash of the item id).

  Reason: of ~1,500 reviews 59% passed untouched and 2% were returned; what matters (wrong object or hypothesis, a second definition) sits mostly in definitions; a wrong plain lemma statement shows itself in stage 3; the accounts cannot carry eight reviewers on every delivery.
